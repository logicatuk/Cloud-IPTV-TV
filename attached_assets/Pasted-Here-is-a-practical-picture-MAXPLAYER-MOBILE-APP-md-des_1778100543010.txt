Here is a practical picture: MAXPLAYER_MOBILE_APP.md describes a JWT + proxy API design, but artifacts/maxplayer-app in this repo is mainly a direct Xtream/M3U client with a small backend (register / status / playlist). Some markdown items (JWT refresh, signed stream tokens) are not in your current lib/api.ts. Below is what actually bites you in this codebase and what to do first.

Real problems (bugs / product gaps)
1. Player: stream failures are invisible (high impact)
In player.tsx you only react to statusChange for "loading" and never handle "error" (or a stuck loading state). Users can get a black screen or a spinner that never clears with no Retry or explanation.

Fix (conceptually): Subscribe to player error (and/or status === "error"), show a full-screen message + Retry (re-open with a fresh stream URL from Xtream/API). Optionally detect 401/403 on the URL if you later use proxy tokens.

2. “Active” but no usable playlist (backend vs device)
app/index.tsx sends users to /(tabs) as soon as isActive. Pulling the assigned playlist is a separate step (tryFetchFromBackend). That only runs in a narrow useEffect when hasPlaylist is true and hasCredentials is false. If:

the backend says has_playlist before credentials are actually ready, or
assignment happens after the first run, or
tryFetchFromBackend fails silently (catch {} in PlaylistContext),
the user can sit on tabs with no working source until they poke “Check again” on home.

Fix: On focus of home or root layout: if isActive && !hasCredentials, re-check device status + tryFetchFromBackend (and surface errors instead of swallowing them).

3. Watch history: “fast app” / jank
saveProgress in WatchHistoryContext calls reload() after every save, which re-reads all history from storage. The player saves on an interval and on unmount, so you can over-update global state and cause unnecessary list re-renders.

Fix: Debounce reload(), or merge one entry into history in memory and persist async without reloading the full list every time.

4. pollStatus stale error handling (smaller)
In AuthContext, on failure pollStatus returns state.status, but the callback depends on state.status, so in edge cases you can return a stale status. Prefer returning null or reading from a ref on error.

5. Doc vs code (confusion, not a runtime bug)
The markdown assumes JWT, /api/v1/content/..., IP-bound stream tokens. Your app’s api.ts only has device + playlist; live/movies go through lib/xtream.ts. Treat the MD as aspirational or another branch, or update it so contributors don’t chase JWT refresh that isn’t in this tree.

6. Web / HLS (if you care about Expo web)
Same as the doc: HLS in browsers is awkward outside Safari unless you add hls.js (or disable web for IPTV). Not a “bug” on native, but it looks broken on web preview.

Recommendations — priority order (best IPTV experience + speed)
Priority	What	Why
1	Player: errors + retry + clear buffering	Stops the worst user-facing failure mode.
2	Reliable playlist handoff when device is active (poll/focus + non-silent errors)	Stops “activated but empty app” confusion.
3	List performance (Live/Movies/Series): FlatList/FlashList tuning, memo rows, stable keys, reasonable windowSize, avoid heavy work in render	Biggest win for feeling fast on long channel lists.
4	React Query: staleTime, avoid refetch storms, cache categories	Faster tab switches and less network.
5	Throttle watch-history UI updates (debounced reload or partial state)	Less jank while watching.
6	EPG polish (you already have EpgSheet / Xtream short EPG): show now/next on rows, open sheet reliably	Table stakes for a “serious” IPTV UI.
7	Landscape + optional PiP while playing	Expected on TV/tablet/phone.
8	Catch-up / full grid (if Xtream exposes archive)	Big feature, but after reliability and performance.
9	If you move to proxy API + JWT: 401 interceptor + refresh + retry
